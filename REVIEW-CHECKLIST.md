# Portfolio Review Checklist

Use this checklist before committing any new portfolio artefact.

## Ownership and purpose

- [ ] The business purpose of the artefact is clear.
- [ ] Christopher owns the new work or has permission to use the source.
- [ ] The artefact was created specifically for the portfolio.
- [ ] The source treatment is recorded in `SOURCE-PROVENANCE.md`.

## Named-company boundary

- [ ] Company names appear only where needed for public career chronology or an explicitly approved owned venture.
- [ ] No named company is connected to internal metrics, budgets, programmes, customers, systems, fields, incidents or confidential outcomes.
- [ ] No employer name appears in an anonymised case study, framework example or synthetic demonstration.
- [ ] No combination of role, date, technology, metric and event indirectly identifies confidential work.
- [ ] Internal programme names, product names and terminology have been removed.
- [ ] Exact dates, volumes, headcounts, team ratios and technology combinations have been generalised where identifying.
- [ ] No original slide, spreadsheet, screenshot, export or document has been uploaded.

## Customer, employee and partner confidentiality

- [ ] No customer, prospect, employee, partner, supplier, parent, child or user name appears.
- [ ] No real email domain, account name, identifier, CRM record, timestamp or contact detail remains.
- [ ] No production data has been anonymised and reused; it has been replaced with synthetic data.
- [ ] No private pricing, contract, support, usage or commercial information appears.

## Personal information

- [ ] No personal email addresses, phone numbers, home addresses or precise location are present.
- [ ] No family, child or private social information is present.
- [ ] No identity, payroll, banking, tax, legal or health information is present.
- [ ] No personal photograph is included without explicit approval and metadata review.

## Data and examples

- [ ] All example records are synthetic.
- [ ] Synthetic names and domains are clearly fictional.
- [ ] No real CRM IDs, account IDs, campaign IDs or timestamps remain.
- [ ] Metrics are supportable, safely generalised and non-identifying.
- [ ] No outcome has been invented or overstated.
- [ ] Facts, assumptions, inferences and recommendations are clearly separated.

## Security

- [ ] No credentials, tokens, API keys, passwords or connection strings are present.
- [ ] No private links contain embedded access parameters.
- [ ] Secret scanning has passed.
- [ ] File names have been checked for sensitive terms.
- [ ] Git history has been checked if a sensitive file was ever added.

## Documents and metadata

- [ ] Hidden tabs, comments, speaker notes and tracked changes have been removed.
- [ ] File properties and author metadata have been reviewed.
- [ ] Embedded images and links have been checked.
- [ ] Archived or compressed files are not included.

## Quality

- [ ] The commercial problem is clear.
- [ ] Christopher's role and decisions are clear without exposing the source organisation.
- [ ] Constraints and trade-offs are visible.
- [ ] The implementation sequence is practical.
- [ ] Governance and adoption are addressed.
- [ ] Measures are defined and evidence status is stated.
- [ ] Limitations and uncertainty are visible.

## Repository boundary

- [ ] Nothing has been copied from the ThinkBud repository.
- [ ] Nothing has been copied from another code repository without explicit approval.
- [ ] The artefact belongs in this repository.
- [ ] Cross-repository links reveal no restricted information.
- [ ] No customer, company or personal data has entered Git history.
